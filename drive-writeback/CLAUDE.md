# CLAUDE.md — drive-writeback

Server-specific guidance for working in this folder. Cross-server rules live in the root `CLAUDE.md` and `../REPO-CONVENTIONS.md` — read those first.

## Status

**Phase 2 ("Mutation surface") implemented — pending deployment.** `update_file_content`, `rename_item`, `move_item`, and `delete_item` are built end-to-end alongside Phase 1's `get_item`/`create_folder`/`create_file`, following the same `DriveGraphClient` (Graph layer) / `DriveWriteService` (dry-run-aware service layer) / `Functions/` tool class shape. `delete_item` is two-step and confirmation-gated (mirroring `outlook-writeback`'s `delete_event`, not the PRD §4.4 literal signature — see `docs/active/PRD-drive-write.md` §4.4's note on this), orchestrated by a new `DriveItemDeletionService` (`DriveWriteback.Graph/Confirmation/`) built on a generic `ConfirmationTokenService` newly extracted to `shared/Sapidus.Writeback.Shared` (see root `CLAUDE.md`'s "What belongs in `shared/`" section for why this one piece of confirmation-token logic — and not `outlook-writeback`'s own still-private copy — qualifies as capability-agnostic). `dotnet test --filter "Category!=E2E"` is green (79 Unit/Integration tests, all offline, no live tenant needed).

**SharePoint document library drives are now rejected outright, not just unhardened.** `DriveGraphClient.ResolveDriveIdAsync` validates any explicitly-supplied `drive_id` by fetching its Graph `driveType` and allow-listing only `"business"`/`"personal"` (any OneDrive, including another user's OneDrive shared with the signed-in user) — anything else, including a SharePoint document library (`"documentLibrary"`) or an unrecognized/missing value, fails closed with the new `SharePointDriveNotSupportedException`. This is a deliberate product decision (Phase 3's hardening was never built and no team site exists to develop it against — see `docs/active/PRD-drive-write.md` §11's Phase 3 note), not a stopgap: PRD §2's "must work against both OneDrive and SharePoint" goal and §13's SharePoint-related success criteria are explicitly marked deferred rather than met. Validated drive ids are cached per-instance (`DriveGraphClient` is a DI singleton) so repeated internal resolutions of the same driveId within one call don't each cost a Graph round trip. All seven tools' `drive_id` parameter descriptions were updated to state this restriction to the calling model. Offline coverage lives in `DriveGraphClientIntegrationTests.cs`. The live E2E test (`GetItemByIdAsync_with_the_signed_in_user_s_own_drive_id_reports_an_allow_listed_driveType`) has now been run against this tenant and passes — the signed-in user's own OneDrive reports `driveType: "business"`, confirming the allow-list's positive path. The rejection path itself still can't be tested live — no SharePoint site exists in this tenant.

**Deployed, including boundary-7b OAuth.** The resource group, storage account, Key Vault, and Function App all exist in Azure (`drive-writeback-rg`), and Easy Auth + a dedicated "Drive Writeback MCP Connector" Entra app are live, serving Claude Desktop and claude.ai — see `DEPLOYMENT.md`'s "Multi-client OAuth via Easy Auth + Entra ID" section. `DRIVE_WRITEBACK_DRY_RUN` is currently `true` — every write tool call resolves and validates but makes no real change, prefixed `[DRY RUN]` in its response — flip deliberately once Desktop/Web tool calls are verified. This server has **no CLI registration** against the deployed endpoint; local dev/testing goes through `func start` + Azurite instead (see `DEPLOYMENT.md`'s "Local smoke test" section).

**All 13 E2E tests now pass against a live tenant** (the original 12 confirmed after the Phase 2 pass shipped; the 13th, for the SharePoint-rejection guard's allow-list, confirmed separately above). Both remaining Phase 1 open questions are resolved: Graph **does** honor `@microsoft.graph.conflictBehavior=fail` as a raw query parameter on the content PUT endpoint, and a content PUT to a path with a missing parent **auto-vivifies** the parent tree rather than 404ing. Neither answer changes this server's own behavior — `create_file` enforces `conflict_behavior` entirely client-side, and `CreateFileAsync` guards against a missing parent before ever reaching Graph — but both are now confirmed facts, not open questions (see `docs/active/PRD-drive-write.md` §11). The first live run of the `conflictBehavior` probe also surfaced and fixed a real test bug: the 409 it got back arrived as a bare `Microsoft.Kiota.Abstractions.ApiException` rather than the `ODataError` subtype the test's catch clause was looking for, because this raw, manually-constructed request has no 409 error factory registered — worth remembering if a future probe test does the same raw-request trick.

Phase 0's original three OneDrive spikes (mkdir-p, eTag/cTag `If-Match`, item-ID shape) remain confirmed passing from that earlier session — see `docs/active/PRD-drive-write.md` §11 for the historical record. SharePoint validation is still deferred, no team site available yet; Phase 1 and Phase 2 are both OneDrive-only, and now enforced as such — see the SharePoint-rejection paragraph above.   - **All 13 have now been run against a live tenant, all passing** — the 3 original Phase 0 spikes, 4 more from Phase 1, 5 from the Phase 2 pass (rename/move/delete-idempotency round trips, `update_file_content` dry-run/real round trip, and the full `DriveItemDeletionService` preview-then-confirm round trip), and 1 confirming the SharePoint-rejection guard's allow-list against this tenant's own OneDrive (`driveType: "business"`). ## Key points for a future implementer

- Scopes: `Files.ReadWrite.All` and `Sites.Read.All` only (PRD §6) — no `Sites.ReadWrite.All`.
- `DriveGraphClient` (in `DriveWriteback.Graph/DriveGraphClient.cs`) now carries the original Phase 0 spike methods (`CreateFolderSegmentAsync`, `GetItemByPathAsync`, `GetItemByIdAsync`, `ReplaceTextContentAsync`, `DeleteItemAsync`), Phase 1's real tool-surface methods (`CreateFolderPathAsync`, `TryGetItemByPathAsync`, `ResolveFolderPathAsync`, `CreateFileAsync`, `GetItemAsync`, `CreateWithSilentRefreshAuth`), and Phase 2's real tool-surface methods (`ReplaceContentByIdAsync`, `RenameItemAsync`, `MoveItemAsync`, `DeleteItemByIdAsync`, `TryGetItemByIdAsync`, plus the private shared `PatchItemAsync`). Every method takes an optional `driveId`, mirroring the PRD §5 addressing model (omitted → signed-in user's own OneDrive). Phase 2's methods are all id-based, not path-based — the service layer resolves `path_or_id` via `GetItemAsync`'s discriminator first, then acts by id.
- **`TryGetItemByIdAsync` exists because `GetItemByIdAsync` doesn't catch 404** (same as `GetItemByPathAsync`/`TryGetItemByPathAsync`'s split) — a real bug was caught while writing `DriveItemDeletionServiceTests`: `ConfirmDeletionAsync`'s already-deleted-is-success branch (PRD §7) was checking for a null result that `GetItemByIdAsync` could never actually produce on a 404, since it lets `ODataError` propagate uncaught. Fixed before it shipped; worth remembering if a future `GetItemByXxxAsync` addition needs the same existence-check treatment.
- **`delete_item`'s confirmation mechanism deliberately diverges from the PRD §4.4 literal signature.** The PRD's tool-detail table lists only `drive_id`/`path_or_id`/`expected_name`/`recursive`, but its own prose says delete_item needs "the same posture as `delete_event`" — which actually enforces confirmation via a stateless HMAC-signed token forcing a real two-call round-trip, something `expected_name` alone doesn't provide (it only guards drift, not against the model skipping confirmation entirely). `DeleteItemTool` adds `confirmation_token` beyond what §4.4 lists. `DriveItemDeletionService` (`DriveWriteback.Graph/Confirmation/`) orchestrates: reads go straight to `DriveGraphClient`; the actual delete routes through `DriveWriteService.DeleteItemAsync` (internal) so it inherits dry-run gating, unlike `delete_event` which has no dry-run concept. `expected_name` and the `recursive`/`Folder.ChildCount` guard are both re-checked at confirm time against a fresh read, not trusted from the preview — closing the race where the item gets renamed or a folder gains children in the window between the two calls.
- **The confirmation-token primitive (`ConfirmationTokenService`) lives in `shared/Sapidus.Writeback.Shared`, not copied into this server.** It's generic over an opaque resource-id string, has no Graph dependency, and (unlike boundary-7a auth code) doesn't touch anything that would couple this server's failure modes to another's — see root `CLAUDE.md`'s "What belongs in `shared/`" section and `REPO-CONVENTIONS.md` §4 for the full reasoning. `outlook-writeback`'s own `DeleteConfirmationTokenService` is still a private, un-migrated copy — a known, deliberate duplication left for a future cleanup pass, not touched by this one.
- **`UploadTextContentAsync` is still Phase-0-spike-only, deliberately not migrated.** The plan for this pass called for moving the E2E fixture's helper onto `CreateFileAsync` and deleting `UploadTextContentAsync` once it did — that migration was deliberately deferred: the three original Phase 0 E2E tests that use it are the only currently-verified-green live tests in this folder, and this pass couldn't re-run them to confirm the swap didn't regress anything. `CreateFileAsync` is additive alongside it, not a replacement yet. Do the migration (and then delete `UploadTextContentAsync`) once someone can run the E2E tier live and confirm the swap.
- **Prefer id-based addressing over colon-path addressing for anything just created in the same call chain.** Real Graph behavior, found the hard way (PRD §11): colon-path resolution (`Items["root"].ItemWithPath(path)`) of a folder immediately after creating it can lag, and the failure mode isn't a clean 404 — a `/children` POST against an unresolved colon-path silently lands at the drive root instead. `CreateFolderPathAsync`/`ResolveFolderPathAsync` chain by the `id` each create/lookup returns rather than re-deriving path strings.
- **Path-vs-ID discriminator (`DrivePath.LooksLikeItemId`):** an id never contains `/`, but that alone is insufficient (a root-level filename like `"notes.md"` also contains none). The heuristic adds no-dot/all-alphanumeric/length≥20 (the one observed live OneDrive item id was 34 chars). `GetItemAsync`/`get_item`'s response states which interpretation was used, so a misclassification is visible rather than silent — this is a heuristic, not a guarantee, and a hyphenated SharePoint id (not yet observed) could misclassify as a path.
- **Dry-run (`DriveWriteOptions.DryRun`, default `true`) lives entirely in `DriveWriteService`** — `DriveGraphClient` stays a dumb, dry-run-agnostic Graph wrapper. Flip via the `DRIVE_WRITEBACK_DRY_RUN` app setting/env var, no code change needed.
- The Graph SDK's generated `Me.Drive.Root` only exposes `GetAsync`/`Content` — no `Children`, no `ItemWithPath`. Folder/file operations route through `Drives[driveId].Items["root"]` (or `Items[itemId]` once an id is known) instead (Graph's documented `"root"` item-id alias), which does support both. Verified by compiling against the real `Microsoft.Graph` 6.2.0 assembly, not assumed — see the doc comment on `DriveGraphClient` itself if this needs revisiting on a future SDK upgrade. Confirmed the same way: `Content.ContentRequestBuilder`'s `PutAsync`/`ToPutRequestInformation` accept only `Microsoft.Kiota.Abstractions.DefaultQueryParameters` — no typed `conflictBehavior` support — which is why `create_file` enforces conflict behavior client-side instead.
- No Native AOT (decided against — see PRD §10). Full `Microsoft.Graph` SDK, matching `outlook-writeback`.
- No provisioning script — `DEPLOYMENT.md` is the sole source of truth for standing this up or rebuilding it, mirroring `outlook-writeback`'s posture exactly. An earlier `scripts/Register-EntraApp.ps1` wrapper was tried and removed: it hit a real eventual-consistency issue in its admin-consent verification (see `DEPLOYMENT.md` step 5's "known issue" note) that a second copy of the same logic just added a place for it to hide.
- **`ResolveDriveIdAsync` is the one place every method resolves its effective drive id through, and now also this server's SharePoint-rejection enforcement point.** An omitted `driveId` resolves the signed-in user's own OneDrive (`/me/drive`, never SharePoint, so no further check). An explicit `driveId` is validated by fetching its Graph `driveType` and allow-listing only `"business"`/`"personal"` — anything else (SharePoint's `"documentLibrary"`, or an unrecognized/missing value) throws `SharePointDriveNotSupportedException`. Fails closed deliberately: an unanticipated Graph response value must not silently pass. Validated ids are cached in a `ConcurrentDictionary` for the life of the singleton, since a drive's type never changes and several call paths (e.g. `CreateFileAsync`'s parent/target checks) re-resolve the same id internally. `StubHttpMessageHandler` (test project) answers the resulting `GET /drives/{id}` with `driveType: "business"` by default so this didn't require touching every pre-existing offline test — only tests that specifically exercise rejection pass `ownDriveType` to override it.
